Núcleo de lógica

Rule.ts

¿Qué problema resuelve? Decide si UN personaje viola UNA regla puntual. No sabe nada de las demás reglas activas ese día — esa combinación la arma Day.ts. La pieza más pequeña y más citable del proyecto: 55 líneas, una sola responsabilidad.

¿Por qué se llama así? Modela literalmente una regla de la agencia. No se llama Validator porque no valida datos genéricos: representa una regla concreta del mundo del juego, con su propio día de origen y descripción.

Explicación línea por línea

export class Rule {
  #day: number;
  #property: string;
  #forbiddenValue: any;
  #description: string;
#day → el día en que esta regla "nace". Trampa de examen: no es necesariamente el día calendario en que se activa en la partida — es un ID de agrupación que dias.json remapea (ver pregunta 7 del FAQ y la tabla de la sección Game.ts).
#property → string que dice QUÉ mirar del personaje: "tieneCuernos", "ojosAmarillos", "region", "sello", "especieProhibida", "selloAlien".
#forbiddenValue: any → es any porque distintas reglas comparan tipos distintos: true/false para cuernos, un string para región/sello/especie, null para selloAlien.
isViolated(character: Character): boolean {
    switch (this.#property) {
      case "tieneCuernos":
        return character.obtainHaveHorns === this.#forbiddenValue;
      case "ojosAmarillos":
        return character.obtainYellowEyes === this.#forbiddenValue;
      case "region":
        return character.obtainPassport.obtainRegion === this.#forbiddenValue;
      case "sello":
        return character.obtainPassport.obtainStamp === this.#forbiddenValue;
      case "especieProhibida":
        return character.obtainPassport.obtainDeclaredSpecie === this.#forbiddenValue;
      case "selloAlien":
        return false;
      default:
        return false;
    }
  }

La línea más importante de esta clase: case "selloAlien": return false; — esta regla nunca se "viola" en el sentido de "rechazar". Le dice al jugador CÓMO aprobar a un alien (sello azul), no A QUIÉN rechazar. Si devolviera true alguna vez, Game.decide() rechazaría a todos los aliens — justo lo opuesto a la regla real.

switch (this.#property) es la ÚNICA excepción documentada a "nada de switch" — es exactamente el caso para el que existe: una variable, varios valores discretos, sin rangos ni combinaciones.

Argumentos de defensa

  • Decisión más defendible: una sola clase genérica en vez de 6 subclases (HornsRule, etc.) — con reglas tan simples, una jerarquía sería sobre-ingeniería.
  • Alternativa descartada: un Map propiedad→getter. Prohibido en el curso, y menos explícito que el switch.
  • Bug real corregido: una versión temprana llamaba métodos en español (tieneCuernosVisibles()) sobre clases ya en inglés — se corrigió del lado de Rule.ts (ver docs/diario.md, 2026-08-12).

Day.ts

¿Qué problema resuelve? Agrupa las reglas activas de un día y decide, para UN personaje, cuál de todas viola (si viola alguna). El paso intermedio entre "una regla suelta" y "el estado completo de la partida".

evaluateCharacter(character: Character): Rule | null {
    const violatedRule = this.#activeRules.find((rule: Rule) => rule.isViolated(character));
    if (violatedRule === undefined) {
      return null;
    }
    return violatedRule;
  }
.find() devuelve la PRIMERA regla activa violada, o undefined. El if convierte ese undefined en null a propósito: Rule | null es la única forma permitida de "esto puede no existir", y todo el resto del código compara contra null, nunca undefined.
Caso límite a tener presente: si un personaje viola VARIAS reglas, esta función solo devuelve la primera del array — suficiente para "hay que rechazarlo", pero significa que buyHint() (tienda) revela solo UNA razón aunque haya más. Es una simplificación consciente, no un bug.

Argumentos de defensa

  • Decisión más defendible: que Day no sepa nada de JSON — solo modela el concepto. Permite testear evaluateCharacter() con datos armados a mano.
  • Conexión con el resto: Game.decide() llama a currentDay.evaluateCharacter() en cada decisión — es el punto de entrada real de toda la lógica de reglas.

export function addCredits(name: string, amount: number): void {

#chargeDailyCost() y por qué NO vive en #startDay()

#chargeDailyCost(): void {
    const activeRulesCount = this.currentDay.getActiveRules().length;
    const cost = 2 + activeRulesCount;
    this.#dayCharge = cost;
    this.#money -= cost;
}
Pregunta trampa: "¿por qué no lo llamás desde #startDay(), si ahí es donde arranca el día?" → porque #startDay() también lo llama loadProgress() cada vez que se recarga la página a mitad de partida. Si el cobro viviera ahí, se cobraría de nuevo en cada refresco del navegador. Viviendo en endDay(), se cobra una sola vez, exactamente cuando un día NUEVO empieza de verdad.

#generateVisitor() — la lógica más intrincada

~200 líneas, la función con más densidad de decisiones no obvias de todo el proyecto.

const goal = this.#days[this.#dayNumber - 1].getVisitorGoal();

problematicRatio sube con el día (día 1 ≈ 1 de 6, día 5 ≈ 4 de 6), calibrada con el objetivo de visitantes del día — que ya NO limita cuántos hay (el día dura por tiempo), pero sigue siendo el denominador.
const activeProperties = activeRules
    .map((rule: Rule) => rule.getProperty())
    .filter((property, index, properties) => properties.indexOf(property) === index)
    .filter((property) => property !== "selloAlien");
Se elige primero la CATEGORÍA de regla a violar, y recién después una regla puntual dentro de ella. Por qué: el día 4 activa 4 reglas de especieProhibida a la vez — si se sorteara directo entre reglas individuales, esa categoría pesaría 4 veces más sin que nadie lo decidiera a propósito.

Argumentos de defensa de Game.ts

  • La decisión más fuerte de defender de todo el proyecto: Game.ts no importa nada de DOM, no usa setTimeout. Todo lo que necesita de "tiempo real" se lo pasa main.ts por parámetro — esto permite testear partidas completas (tienda incluida) sin navegador.

  • Bug evitado a tiempo: el cobro diario casi vivió en #startDay() — se pensó a tiempo en el caso de loadProgress() antes de implementarlo mal.

pauseDayTimer() se dispara tanto por la pausa manual del jugador como por una reacción de la Jefa. resumeDayTimer() nunca reinicia el día entero: reprograma el cierre con el tiempo REAL restante (DAY_DURATION_MS - dayElapsedMs).

function currentDayElapsedMs(): number {
  if (dayResumedAt === null) {
    return dayElapsedMs;
  }
  return dayElapsedMs + (performance.now() - dayResumedAt);
}
Dos variables en vez de una: dayElapsedMs (tiempo YA acumulado) y dayResumedAt (instante en que arrancó el tramo actual, o null si está pausado). Con un solo timestamp no se podría pausar sin perder la cuenta real.
function onDayTimerExpire(): void {
  if (game === null) return;
  if (resolvingDecision) {
    dayEndsOnRelease = true;
    return;
  }
  const dayBefore = game.dayNumber;
  game.endDay();
  afterDecision(dayBefore);
}
Condición de carrera real, ya resuelta: si el timer vence justo mientras el jugador suelta un sello (animación de ~1.5s), no se corta el día a la mitad — se marca dayEndsOnRelease = true y recién se cierra el día cuando la decisión en curso termina de procesarse. Sin esto, se disparaban DOS pantallas de resultado casi juntas (bug real documentado en el diario).

Preguntas frecuentes de defensa oral — respuestas preparadas

1"¿Por qué elegiste TypeScript vanilla sin framework?"
Fue una restricción del curso, no una elección personal — pero la defendería igual: el juego tiene un número fijo y chico de pantallas y un solo estado global (Game), así que un framework de componentes no resolvía ningún problema real que no pudiera resolver con clases simples y document.querySelector.
2"¿Cómo se prueba este código sin abrir el navegador?"
Game.ts no depende del DOM ni del navegador para nada. Eso me permitió escribir docs/test-temporal.mjs: un script que corre con Node, simula fetch leyendo archivos del disco y localStorage con un objeto en memoria, y juega partidas completas —tienda y economía incluidas— sin ningún navegador. Tengo 15 baterías de test ahí.
3"¿Qué pasa si dos personas juegan el mismo día en la misma máquina?"
Se pisarían: Storage.ts usa claves fijas, no separadas por usuario del sistema. Lo que SÍ está separado es el nombre del inspector dentro del juego — los créditos se guardan por nombre, así que dos "jugadores" con nombres distintos tienen su propio ranking, aunque compartan la partida en curso.
4"¿Por qué Rule.isViolated() devuelve true cuando algo está MAL?"
La pregunta que la clase responde de verdad es "¿esta regla se incumple?", no "¿está en regla?" — porque un personaje puede estar en regla frente a UNA regla y ser rechazado por otra distinta. Day.evaluateCharacter() necesita preguntarle a cada regla, una por una, "¿VOS te violás con este personaje?", y la respuesta directa a eso es isViolated().
5"¿Cuál fue la parte más difícil de programar de tu lado?"
Game.#generateVisitor(), sin dudarlo. No es difícil el concepto, es difícil que todas las combinaciones queden coherentes: que un Yokai mintiendo no mienta con una palabra ya prohibida por otra regla, que el rostro alien no pise el único rasgo real que lo hace problemático, que la proporción del día no se rompa por un caso borde.
6"¿Cómo te coordinaste con tu compañero?"
Con ramas separadas e integraciones periódicas — no siempre a la primera: mi Rule.ts llamaba métodos en español sobre clases que Mike ya tenía en inglés; mi main.ts usaba campos (obtainNose) que él ya había sacado. Más reciente: en un merge grande, mi pantalla de Opciones quedó con una versión vieja SIN ningún marcador de conflicto — aprendí que la ausencia de marcadores no prueba que el merge automático eligió bien.
7"En reglas.json el sello plateado dice 'dia': 6, pero se activa el día 7. ¿Es un error?"
No, es intencional aunque el nombre pueda confundir. "dia" ahí es un ID de agrupación, no el día calendario — eso lo decide dias.json (campo reglasActivas). Si tuviera que rehacerlo, le pondría otro nombre al campo (ruleId) para evitar justo esta confusión — es una crítica válida, prefiero reconocerla a que me la señalen.
8"¿Por qué el dinero puede quedar en negativo y la partida sigue?"
Es diseño explícito: la única condición de derrota es Game.isLost(), que mira solo #errors >= 4. El dinero es un segundo sistema de progreso (ranking, final alternativo), no una segunda forma de perder. Probado en el TEST 11.
9"¿Por qué separaste el audio en dos clases?"
Su comportamiento interno difiere de una forma que importa: los efectos se clonan (pueden sonar varios a la vez), la música nunca se clona (un solo loop). Forzarlas juntas habría significado un if interno preguntando qué tipo de sonido es, en vez de que cada clase resuelva su propio caso.
10"¿Cómo decidiste los precios de la tienda?"
